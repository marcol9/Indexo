# Home Task: Payment Intake API

Thanks for taking the time to do this. Plan for 1-2 hours. If something
drags on longer, stop and write in your README what you would do next

## What we need

A small payment intake service. Clients submit payments over HTTP and can
list what has been accepted. Build it from scratch in TypeScript (Node.js).
Project setup, structure, framework choice and internal design are up to you.

## API

### POST /payments

Takes a JSON body like this:

```json
{
  "paymentId": "11111111-1111-1111-1111-111111111111",
  "amount": 100.50,
  "currency": "EUR",
  "debtorIban": "LV97HABA0012345678910",
  "creditorIban": "LV12PARX0000000000001",
  "reference": "Invoice 42"
}
```

Treat the body as untrusted input. Fields may be missing, malformed or of
the wrong type. A bad request should get an error response, never crash the
server.

### GET /payments

Returns the accepted payments currently in the store. This response shape
is fixed, we check it with automated tests:

```json
{
  "payments": [
    {
      "paymentId": "11111111-1111-1111-1111-111111111111",
      "amount": 100.50,
      "currency": "EUR",
      "debtorIban": "LV97HABA0012345678910",
      "creditorIban": "LV12PARX0000000000001",
      "reference": "Invoice 42"
    }
  ]
}
```

Rules: status 200, payments in the order they were accepted, `reference`
omitted or null when not provided, empty store returns `{ "payments": [] }`.
You may add extra fields to a payment object if you have a reason, but the
fields above must be present with these names and types. Numbers are
compared as numbers: 100.5 and 100.50 are the same value, don't worry about
formatting.

## Requirements

Validation rules for a payment:

- `paymentId`: required, non-empty string, generated by the client. It
  uniquely identifies a payment: one paymentId means one payment, no matter
  how many times it is submitted.
- `amount`: required, positive number, max 2 decimal places
- `currency`: one of EUR, USD, GBP
- `debtorIban`, `creditorIban`: required. A basic sanity check is enough:
  two letters followed by digits/letters, 15 to 34 characters total.
  Whether you accept lowercase letters is your call, we don't test it.
  Please don't implement full mod-97 IBAN validation, it's not the point
  here.
- `reference`: optional string

Store accepted payments in memory, no database. Write the persistence code
so it could be swapped for a real store later.

One thing to be clear about: the store is just a record of accepted
payments. This service does not track account balances and should not check
whether the debtor has enough money. That would be the ledger's job, and the
ledger is a different service. Here an IBAN is just a validated string.

Clients retry, so the same paymentId may arrive more than once. A repeat
must not create or process a duplicate, and GET /payments must show it
exactly once. What the repeated POST returns is your call, just be ready to
explain why.

Pick HTTP status codes you think fit each outcome, and be ready to explain
your choices. One constraint, because we test this automatically:
an accepted payment must return a 2xx code, a rejected one a 4xx code, and
bad input must never produce a 5xx or crash the server. The repeated
submission case is exempt: 2xx or 4xx are both fine there, it's your design
decision.

The file [`requests.http`](./requests.http) contains sample requests
covering the kinds of cases we will test: valid ones, a retry, and several
broken ones. We may also try other inputs, but always within the rules
described above. Run it with the VS Code REST Client extension, a JetBrains
IDE, `npx httpyac`, or just copy the bodies into curl or Postman.

## Technical constraints

- TypeScript, Node.js 20+
- `npm install && npm start` should be all it takes, server on
  http://localhost:3000
- In-memory storage only, no database, no external services
- No auth, no Docker, no CI. A service running on your machine is all we want
- Framework is your choice: Express, Fastify, plain node:http, whatever you
  would actually pick for something this size

## A few ground rules

Structure the code as you would in a real project, scaled to the size of the
task. Tests are not required, but a few well-chosen ones count in your
favor.

AI tools are fine (Copilot, Claude, ChatGPT, whatever you use). At the
interview you will walk us through the code and we will change it together,
so you own every line no matter who typed it.

Don't gold-plate. Sensible shortcuts plus a note about them beat unfinished
ambition.
